# 개인 페이지 k6 테스트 — 관리자 API 자동 준비

대상 기본 주소: `http://43.202.5.26:8000`
사용자가 제공한 기존 `student-flow.js`의 관리자 API 방식을 재사용한다.
DB 직접 접속, JWT 비밀키, 학생 JSON 수동 작성, 학생 로그인 입력이 필요 없다.
공유 페이지는 이번 테스트에서 제외한다.

## 실행

관리자 정보를 파일에 저장하지 않고 실행하려면 프로젝트 루트에서 다음 명령을 사용한다.
아이디는 Enter로 `admin`을 선택하고 비밀번호를 입력한다. 비밀번호는 화면에 표시되지 않는다.

```powershell
.\backend\tests\load\run.ps1 -PromptAdmin
```

`backend/.env`의 `ADMIN_USERNAME`, `ADMIN_PASSWORD`가 대상 서버와 같으면 바로 실행한다.
셸 환경변수가 있으면 파일보다 우선한다. DB/JWT/AI 설정은 읽어 사용하지 않는다.

```powershell
# 본인 조회 + 부스 인증, 각각 초당 1여정 2분
.\backend\tests\load\run.ps1

# 본인 페이지: 서로 다른 학생 500명이 10초 안에 진입
.\backend\tests\load\run.ps1 -Journey own -Profile burst10

# 부스 인증: 서로 다른 학생 500명이 거의 동시에 흐름 시작
.\backend\tests\load\run.ps1 -Journey visit -Profile sync500

# 7개 부하 구성 × 본인 조회/부스 인증 = 14회, 실패하면 중단
.\backend\tests\load\run.ps1 -Profile all
```

서버 관리자 정보가 로컬 `.env`와 다르면 `admin.example.env`를 참고해
`backend/.env.k6`에 두 값만 넣고 실행한다. 파일은 Git 제외 대상이다.

```dotenv
ADMIN_USERNAME=해당서버의_관리자아이디
ADMIN_PASSWORD=해당서버의_관리자비밀번호
```

```powershell
.\backend\tests\load\run.ps1 -EnvFile .\backend\.env.k6
```

다른 서버는 `-BaseUrl`로 지정한다. `-BoothCode`를 생략하면 관리자 API의 기존 부스 목록에서
하나를 선택한다. 기존 부스가 없으면 임시 테스트 부스를 만들고 종료 시 정리한다.
명시한 부스 코드가 없으면 오타로 보고 중단한다.
`-CheckOnly`는 로그인 없이 헬스체크만 수행한다.

## 자동 실행 흐름

1. 관리자 로그인 및 배포 서버 API 명세 확인.
2. `POST /api/admin/students/test`로 이번 실행만의 테스트 학생 발급.
3. `POST /api/admin/students/test/{id}/token`으로 학생 토큰 발급.
4. `POST /api/sessions/complete`에 합성 페르소나를 전달해 완료 프로필 준비.
5. k6로 개인 페이지 조회 또는 부스 인증 부하 측정.
6. `DELETE /api/admin/students/{id}`로 **이번에 발급한 계정만** 정리.

이전 코드의 `DELETE /api/admin/students/test` 전체 삭제는 사용하지 않는다.
기존 학생·테스트 계정·부스는 삭제하지 않는다. 부스 방문 기록은 이번 테스트 학생에만 생기고,
계정 정리 시 서버의 cascade로 함께 삭제된다. AI 생성·사진 업로드는 호출하지 않는다.
준비와 정리는 k6 측정 구간 밖에서 수행하며 준비 동시성은 5다.
각 부하 구성/여정마다 새 계정을 준비해 신규 방문이 중복 방문으로 바뀌는 것을 방지한다.

## 측정 범위

### 50개 부스 / 3,000명 / 3분 혼합 테스트

```powershell
.\backend\tests\load\run.ps1 -PromptAdmin -Profile mixed
```

기존 부스와 별도로 임시 부스 50개, 서로 다른 테스트 학생 3,000명을 자동 생성한다.
3,000 VU에 학생을 한 명씩 배정하고 0~15초 안에 첫 조회를 시작한다.
3분 동안 개인 페이지 조회 50%, 무작위 부스 조회 20%, 방문 인증 후 개인 페이지 확인 30%로
행동을 선택하며 행동 사이에 3~8초를 기다린다. 비율은 행동 선택 확률이며 실제 횟수와 다를 수 있다.
각 학생이 여러 부스를 선택할 수 있고 재방문 시 중복 여부와 방문 시각 유지도 확인한다.
응답 지연이 길어지면 학생들의 다음 행동도 늦어진다. 고정 초당 요청량 테스트가 아니다.

측정은 3분, 진행 중인 요청의 종료 대기는 최대 30초다. 계정·부스 준비/정리는 별도 시간이다.
결과는 `results/mixed-<ID>/mixed.json`, 범위는 `scope.json`에 남긴다.
학생과 임시 부스만 개별 삭제하고 학생 토큰 파일도 정리한다.
기존 부스가 있으면 개인 페이지 응답에는 그 부스들도 포함되지만 방문 대상은 만든 50개로 제한한다.
`-Profile all`에는 이 별도 혼합 시나리오가 포함되지 않는다.

아래 표는 기존 개별 시나리오의 측정 범위다.

| Journey | 호출 |
|---|---|
| own | `GET /api/students/me` |
| visit | 프로필 → 부스 조회 → 신규 인증 → 프로필 → 중복 인증 → 프로필 |
| all | 위 두 흐름을 독립적으로 차례대로 실행 |

방문 흐름은 1여정당 6개 HTTP 요청이다. `burst10`은 초당 50여정이므로
조회 테스트는 초당 약 50요청, 방문 테스트는 최대 약 300요청이다.
동시 요청 테스트는 여정의 **첫 요청**을 동기화하며, 이후 POST는 앞선 조회가 끝난 뒤 실행한다.

**카드 이미지가 없는 완료 프로필을 테스트한다.** API로 합성 페르소나는 저장하지만 카드/사진을
생성하지 않는다. 카드 URL 서명, 이미지 전달, 브라우저 렌더링 성능은 이 테스트의 검증 범위 밖이다.
현재 배포 서버의 명세에는 `competencies`가 없어 역량 점수 검증을 제외한다.
지원되는 서버에서는 자동으로 점수 증가/중복 방지를 검사한다. 실제 명세와 검증 범위는
각 결과 폴더의 `scope.json`에 남긴다. 프로필에 방문 시각이 없으면 해당 비교만 생략하되
POST 응답의 첫 방문 시각이 중복 인증에서 유지되는지는 검사한다.

## 부하 구성과 기준

| Profile | 부하 |
|---|---|
| smoke | 초당 1여정, 2분 |
| steady | 초당 10 → 20 → 35 → 50여정, 각 5분 |
| burst10 | 학생 500명이 10초 동안 한 번씩 진입 |
| burst5 | 학생 500명이 5초 동안 한 번씩 진입 |
| sync100 / sync300 / sync500 | 지정 학생 수가 거의 동시에 한 번씩 시작 |

집중/동시 부하 뒤에는 5분간 초당 3회 본인 프로필 조회로 회복을 검사한다.
조회는 배출 대기 12초, 방문은 최대 6개 요청을 고려해 62초다.
smoke 방문 계정은 11명, steady 방문은 550명을 준비해 VU별로 다른 학생을 사용한다.
반복 구간의 같은 학생은 첫 방문 뒤 중복 방문으로 처리하고 두 경우를 별도 집계한다.

- 각 API `api_elapsed_ms` p95 < 800ms, 연결/TLS 시간 포함.
- 전체 여정 `profile_elapsed_ms` p95: 본인 조회 < 800ms, 부스 흐름 < 4800ms.
- `profile_valid` 100%, HTTP 실패율 < 1%.
- `profile_completed` 계획 여정 수와 일치, `dropped_iterations` 0.
- burst/sync 방문의 `new_visits`는 참여 학생 수와 일치.
- sync 요청 시작 지연 최댓값 < 1초. 초과하면 부하 발생기 병목도 조사.

중복 인증은 `already_visited=true`, 방문 상태/시각 유지 여부를 확인한다.
500명 테스트는 한 계정 재사용이 아니라 서로 다른 테스트 계정을 사용한다.
통과는 설정한 부하/범위의 통과이며 행사 전체 수용 능력이나 브라우저 로딩 시간 보장은 아니다.

## 결과와 중단

`backend/tests/load/results/api-<실행 ID>/`에 결과 JSON과 검증 범위를 저장한다.
계정 ID만 담긴 `*-owned.json`은 정리 성공 시 빈 배열이 된다.
정리 실패·강제 프로세스 종료로 ID가 남으면 그 계정만 관리자 API로 정리한다.
전체 테스트 계정 삭제 API는 호출하지 않는다. 생성 응답 유실 시 서버에 기록만 남을 수 있으므로
실행 이름 접두사 `k6-profile-`를 확인해야 하며 다른 실행 계정까지 일괄 삭제하지 않는다.
학생 토큰 파일은 정상 종료/실패 처리 시 제거한다. `--http-debug`는 사용하지 않는다.

실측 결과는 같은 폴더의 `RESULTS.md`에 기록한다.
