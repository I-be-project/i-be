# 나Be한마당 — 프로젝트 문서

기획·설계·운영 기록을 모아둔다. 코드는 [루트 README](../README.md) 참고.

## 폴더를 수명으로 가른다

문서를 **성격이 아니라 수명으로** 나눈다. 이러면 "이 문서 아직 유효한가?"에
폴더 이름만 보고 답할 수 있다.

| 폴더 | 수명 | 내용이 틀렸을 때 | 파일명 |
|---|---|---|---|
| [`guides/`](guides/) | **살아있음** — 지금의 사실 | **고친다** | 날짜 없음 |
| [`issues/`](issues/) | **박제** — 그때의 기록 | 고치지 않는다 | `YYYY-MM-DD-` |
| [`notes/`](notes/) | **박제** — 그때의 기록 | 고치지 않는다 | `YYYY-MM-DD-` |
| [`superpowers/`](superpowers/) | 자동 생성 | 건드리지 않는다 | `YYYY-MM-DD-` |

박제 문서는 **내용을 갱신하지 않는다.** 당시 판단이 그랬다는 게 기록의 값어치다.
사실과 달라졌으면 문서 첫머리에 경고 배너를 달고 현행 문서를 링크한다
(예: [`notes/2026-06-27-백엔드-초기-배포-구축.md`](notes/2026-06-27-백엔드-초기-배포-구축.md)).

다만 **깨진 링크는 고친다.** 링크는 판단이 아니라 길 안내다.

## 어디에 쓸지 판단하기

```
지금도 사실이어야 하는 문서인가?
├─ 예 → guides/           배포 방법, 아키텍처, API 명세
└─ 아니오
   ├─ 개발하다 삽질했거나 인프라 판단을 내렸나?
   │   └─ 예 → issues/    코드·커밋으로 복원 불가능한 맥락
   └─ 분석·조사·설계 기록인가?
       └─ 예 → notes/     리스크 분석, 용량 점검, 지난 설계
```

## issues/ — 삽질과 인프라 판단

[`issues/README.md`](issues/README.md)에 전체 색인이 있다.

**남기는 기준: 코드와 커밋만 봐서는 복원할 수 없는 맥락인가.**
"중요한가"가 아니라 "복원 가능한가"로 판단한다.

| 남긴다 | 남기지 않는다 |
|---|---|
| 진단에 시간이 걸린 것 | 단순 오타·문구 수정 |
| 원인이 의외였던 것 | 코드를 보면 자명한 변경 |
| 재발 가능성이 있는 것 | 일회성 설정 변경 |
| 인프라·배포·보안 판단 | 리팩터링 |

**본문 4섹션** (`kind`에 따라 제목이 달라진다):

| `kind: 디버깅` | `kind: 인프라` |
|---|---|
| `## 증상` | `## 배경` |
| `## 원인` | `## 근거` |
| `## 해결` | `## 조치` |
| `## 교훈` | `## 주의사항` |

**네 번째 섹션이 이 문서의 존재 이유다.** 앞의 셋은 `git show <sha>`로 대부분
복원된다. 복원 안 되는 건 "이게 일반화되는 패턴이고 다음엔 미리 막아야 한다"는
판단뿐이다. **교훈을 쓸 수 없으면 그 이슈는 기록할 가치가 없다.**

색인은 손으로 고치지 않는다:

```bash
python3 scripts/gen-docs-index.py
```

## 폴더 승격 규칙

> **같은 성격의 문서가 3개 모이면 그때 폴더를 만든다. 미리 만들지 않는다.**

빈 폴더와 지켜지지 않는 규칙은 체계의 신뢰를 깎는다. 예정된 승격:

| 지금 | 3개 모이면 |
|---|---|
| `notes/YYYY-MM-DD-결정-<주제>.md` | `decisions/` (ADR) |
| `guides/operations.md` | `guides/runbooks/` |

## 작성 규칙

- 한국어, GitHub Flavored Markdown
- 날짜는 절대 표기. "어제" 같은 상대 표현 금지
- 파일명 슬러그도 한국어 (`2026-08-01-전환-시-이전-대상의-상태가-남는-문제.md`)
- `guides/` 문서는 동작이 바뀌면 함께 갱신하고 하단 변경 이력에 추가
- 이미지·다이어그램은 문서와 같은 폴더에 두고 상대경로로 링크
