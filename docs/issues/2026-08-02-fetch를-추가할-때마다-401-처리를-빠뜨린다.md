# 관리자 화면에 fetch를 추가할 때마다 401 처리를 빠뜨린다

## 증상

관리자 토큰이 만료된 상태에서 화면을 열면 **로그인 화면 대신 엉뚱한 빈 상태**가
보인다. 세 번 다 다른 화면, 다른 커밋이었다.

| 커밋 | 화면 | 만료 시 실제로 보인 것 |
|---|---|---|
| `978be6c` | 회원 목록 사진 | 스켈레톤이 안 걷힘 |
| `3c4b277` | 좌석표 학교 목록 | "해당 학교에 가입한 학생이 없습니다" |
| `87995e5` | 부스 관리 저장·삭제 | 아무 반응 없음 |

`3c4b277`이 특히 나빴다. **토큰 만료를 "학생이 없다"로 오독하게** 만들어서,
운영자가 데이터가 지워진 줄 알 수 있었다.

## 원인

`catch`가 **401을 포함한 모든 실패를 빈 값으로 흡수**했다.

```ts
.catch(() => setSchools([]))   // 401도 여기로 들어온다
```

빈 배열은 "권한이 없다"와 "데이터가 없다"를 구분하지 못한다. 화면은 후자로
해석해서 안내 문구를 띄운다.

**왜 반복됐나 — 공용 헬퍼가 없다.**

401 분기가 필요한 자리마다 아래 5줄을 **손으로 다시 쓴다.**

```ts
if (err instanceof ApiError && err.status === 401) {
  clearToken();
  router.replace(loginPath);
  return;
}
```

2026-08-15 기준 `status === 401`이 **10개 파일에 22번** 등장한다. 추상화가
없으니 새 `fetch`를 쓸 때마다 사람이 기억해내야 하고, 기억은 실패한다.
세 번 터진 건 우연이 아니라 구조의 결과다.

## 해결

각 `catch`에서 401을 먼저 분기하고, 나머지 오류는 **빈 상태가 아니라 에러 배너로**
드러낸다.

→ `frontend/components/console/SeatingView.tsx:125`,
`StudentDetailSidebar.tsx:213`, `BoothListView.tsx:56` 등

```ts
.catch((err) => {
  if (err instanceof ApiError && err.status === 401) {
    clearToken();
    router.replace(loginPath);
    return;
  }
  // 조용히 빈 목록으로 넘기면 "학교가 없다"로 오독된다 — 에러를 드러낸다.
  setError(...);
});
```

## 교훈

**빈 상태(empty)와 실패(error)를 같은 화면으로 처리하면 안 된다.**
"결과가 0건"과 "못 가져왔다"는 사용자에게 완전히 다른 뜻이다. `catch`에서
빈 배열을 세팅하는 코드를 보면 일단 의심한다.

**같은 5줄을 세 번 손으로 쓰게 되면 그게 신호다.** 이 이슈의 진짜 원인은
개별 실수가 아니라 공용 헬퍼의 부재다. 지금도 22곳이 손으로 쓰여 있어
**네 번째가 나올 조건이 그대로 남아 있다.**

새 관리자/운영자 화면에 `fetch`를 추가할 때:

- [ ] `catch`에서 401을 먼저 분기했는가
- [ ] 401이 아닌 실패를 빈 배열·빈 상태로 흘리지 않는가
- [ ] 실패가 화면에 드러나는가 (배너·메시지)

> **미해결 과제**: `handleApiError(err, { onUnauthorized })` 같은 공용 헬퍼로
> 22곳을 묶으면 이 체크리스트 자체가 필요 없어진다. 아직 하지 않았다.
