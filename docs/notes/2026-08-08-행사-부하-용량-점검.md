# 행사 부하·용량 점검 — 2일간 20,000명 규모

작성일: 2026-08-08

## 배경

2일간의 행사에서 **하루 10,000명, 총 20,000명**이 이 시스템을 사용한다. 유입은
**하루 5시간에 집중**된다. 학생 활동은 로그인·설문·부스 인증이고, 페르소나 카드도
발급한다(AI 이미지 API 사용).

현재 구성이 이 규모를 감당하는지 코드·배포 문서 기준으로 점검했다.

**전제 조건 (2026-08-08 확인)**

| 항목 | 값 |
|---|---|
| 앱 서버 | AWS Lightsail 2GB RAM / 2 vCPU / 60GB SSD (`$12/월`) 1대 |
| DB | Supabase **Free 플랜**, 서울(ap-northeast-2) |
| 카드 발급 | **한다** (OpenRouter 이미지 API) |
| 유입 패턴 | 하루 5시간 집중 |

## 요약 — 지금 상태로는 감당하지 못한다

병목은 웹 트래픽이 아니다. 심각도 순으로 셋이다.

| # | 문제 | 심각도 |
|---|---|---|
| 1 | **카드 발급 파이프라인이 운영 코드에 없다** | 🔴 차단 |
| 2 | **AI 비용 약 400~430만원**, 이미지 처리량은 필요량의 45% | 🔴 차단 |
| 3 | **Supabase Free** — 2만 명 PII를 백업 없이 보관 | 🔴 차단 |
| 4 | 단일 인스턴스·단일 워커·LLM 재시도 없음 | 🟠 높음 |

웹 트래픽 자체(§4)는 하루치 작업으로 넘길 수 있다. 1~3번이 실제 리스크다.

## 1. 부하 산정

프론트 코드에서 학생 1명이 실제로 보내는 요청을 셌다.

| 항목 | 횟수 | 근거 |
|---|---|---|
| 로그인/가입 | 1 | `lib/api.ts:192,202` |
| 사진 업로드 | 1 | 최대 10MB (`routers/students.py:19`) |
| **LLM 생성 (q7b·q8·q9)** | **3** | `app/explore/path/page.tsx:135` |
| 답변 저장 | ~10 | 진행 중 5 + 완료 직전 `reconcileAllAnswers` 재전송 5 (`lib/answerSync.ts:181`) |
| 프로필 조회 | 5~15 | 랜딩·성향·부스·프로필 탭 진입마다 (`getMyProfile` 호출 4곳) |
| 부스 조회 + 인증 | 부스 수 × 2 | 10개 부스면 20 |
| 토큰 갱신 | 2~8 | 30분 주기 (`hooks/useKeepTokenFresh.ts:36`) |

**학생 1명당 약 50 요청.**

```
10,000명 × 50요청 = 500,000 요청 / 5시간(18,000초)
→ 평균 28 req/s
→ 학교 단위 파도 유입 시 순간 100~200 req/s
```

설계서의 원래 가정은 **"수백~수천명/일, 동시 수백명"**(`backend-design.md:42-43`)이고,
인스턴스 사양은 **"1차 ~1,000명 규모에 충분"**(`2026-06-27-backend-deploy-lightsail-supabase.md:30`)
기준으로 골랐다. 요청 규모는 그 **3~10배**다.

## 2. 카드 발급 — 운영 코드에 존재하지 않는다 🔴

### 2.1 미구현 지점

| 구성요소 | 상태 |
|---|---|
| `POST /api/cards/generate` | `NotImplementedError` (`routers/cards.py:15`) |
| `GET /api/cards/jobs/{id}` | `NotImplementedError` (`routers/cards.py:21`) |
| 카드 워커 `_claim_next_job` | 스텁 — 항상 `None` (`workers/card_worker.py:54`) |
| `ops.jobs` 큐 테이블 | **마이그레이션 없음** (`supabase/migrations/`에 0001~0008뿐) |
| `CardRepository.create` / `update` | `NotImplementedError` (`repositories/card_repo.py:24,48`) |
| `generated.cards.card_image_key` | nullable — 주석에 "파이프라인 연결 전"이라 명시 |

생성 로직 자체(`services/persona_pipeline.py`)와 합성기(`services/card_renderer.py`)는
완성돼 있다. **큐·저장·API로 연결되지 않았을 뿐이다.**

동작하는 유일한 경로는 `/api/dev/persona-card`인데, 이것은

- 인증이 없고,
- 동기 호출이며(요청 하나가 이미지 2장 생성을 기다림),
- `APP_ENV=local`에서만 라우터가 등록된다 (`app/main.py:114`).

즉 **운영 서버에서는 호출 자체가 불가능하다.**

> ⚠️ 프론트에서 OpenRouter를 직접 호출하는 방식은 채택하지 않는다.
> API 키가 브라우저에 노출되어 누구나 크레딧을 소진시킬 수 있다.

### 2.2 처리량이 필요량의 45%

```
필요:  10,000명 × 2장 / 5시간(18,000초) = 1.11 img/s
현재:  image_concurrency = 10  (app/config.py:107)
       2K 이미지 생성 지연 15~30초
       → 10 / 20초 = 0.5 img/s
```

**5시간에 약 4,500명분.** 필요 동시성은 `1.11 × 지연(20초) ≈ 22`이므로
`IMAGE_CONCURRENCY`를 40~60으로 올려야 한다. 다만 그 시점부터는
OpenRouter/Google 측 rate limit이 새로운 상한이 되므로 **사전 실측이 필수**다.

세마포어는 `AIClient` 인스턴스마다 존재한다(`adapters/ai_client.py:133`).
인스턴스·워커를 늘리면 실효 동시성이 그 배수만큼 커진다는 점에 주의한다.

### 2.3 비용 — 가장 큰 항목

OpenRouter 단가를 조회하고, 공시가가 알려진 모델로 교차검증했다 (2026-08-08 기준).

```
google/gemini-2.5-flash-image  : image_output $0.00003/tok → 1,290tok = $0.039/장
                                 (공시가 $0.039와 일치 → image_output은 토큰 단가)
google/gemini-3.1-flash-image  : image_output $0.00006/tok → 1,120tok ≈ $0.067/장
  (= AI_IMAGE_MODEL 기본값, app/config.py:98)
openai/gpt-5-mini              : 입력 $0.25/M, 출력 $2.00/M
```

프롬프트 크기도 실측했다(`app/core/prompts/question_prompt.py` 빌더 실행):

```
q7b 5,075자 / q8 6,477자 / q9 7,796자  → 학생당 약 19,300자
```

| 항목 | 20,000명 기준 |
|---|---|
| LLM 3콜/명 (gpt-5-mini) | $200 ~ 400 |
| 이미지 2장/명 (2K) | $2,680 |
| **합계** | **≈ $2,900 ~ 3,100 (약 400~430만원)** |

`AI_IMAGE_MAX_RETRIES=2`(최대 3회 시도)를 감안해 **+20% 여유**를 잡는다.
gpt-5-mini는 추론 토큰이 출력으로 과금되므로 실제 사용량은 몇 건 실측해 보정한다.

**절감 레버 (효과순)**

| 방법 | 절감 |
|---|---|
| 배경을 AI 생성 대신 **프리셋 이미지**로 → 이미지 1장/명 | **-$1,340** |
| `AI_IMAGE_MODEL`을 `google/gemini-2.5-flash-image`로 | **추가 -50%** |
| ~~`AI_IMAGE_QUALITY` 2K→1K~~ | **효과 없음** — 출력 토큰 수가 같아 비용이 거의 동일하다. 화질만 손해다. |

### 2.4 CPU·메모리는 문제가 아니다 (실측)

```
render_card: 133 ms/장, peak RSS 82 MB   (Apple Silicon 기준, 2K 입력 2장)
```

2 vCPU 인스턴스에서 3~5배 느려도 장당 0.4~0.7초, 10,000장에 약 100분 CPU다.
합성은 이미 `run_in_threadpool`로 분리돼 이벤트 루프를 막지 않는다
(`services/persona_pipeline.py:68`).

다만 2K 입력 2장을 RGBA로 전개하면 장당 약 50MB이므로, 동시 10건이면 **500MB+**다.
**2GB 인스턴스에서는 OOM 위험**이 있다.

## 3. Supabase Free — 2만 명 PII를 둘 자리가 아니다 🔴

| Free 제약 | 이 행사에서의 의미 |
|---|---|
| **자동 백업 없음** | 학생 2만 명의 실명·학교·학년·반·번호·**비밀번호(생년월일)** 가 백업 없이 존재. 사고 시 복구 불가 |
| DB 500MB | 답변 jsonb 포함 예상 150~250MB — 못 넘진 않지만 여유가 없다 |
| 공유 컴퓨트 | 하루 70만+ 쿼리를 공유 CPU로 처리 |

비밀번호는 정책상 평문 저장이다(`repositories/student_repo.py` 주석,
`services/auth_service.py:145`에서 평문 비교). 정책 자체는 결정된 사항이지만,
**백업이 없는 환경에 평문 PII 2만 건**이라는 조합은 받아들이기 어렵다.

→ **Pro 플랜($25/월) 전환은 선택이 아니라 필수로 본다.** 행사 2일이면 한 달치로 끝난다.

## 4. 웹 트래픽 — 하루치 작업으로 넘길 수 있다

서울 리전이라 DB 왕복이 짧다는 점이 다행이다. 다른 리전이었다면 프로필 API가
초당 15건에서 막혔을 것이다.

| 병목 | 근거 | 영향 |
|---|---|---|
| **uvicorn 워커 1개** | `backend/Dockerfile` CMD에 `--workers` 없음 | 2 vCPU 중 1코어만 사용 |
| **DB 풀 10 고정** | `adapters/db_pool.py:20` + `app/main.py:52`(인자 없이 호출) | 동시 쿼리 상한 |
| **프로필 API가 DB 7왕복** | `services/session_service.py:124-170` (settings→student→booths 전체→visits→session→persona→card) | 탭 전환마다 호출 → 약 70만 쿼리 |
| **S3 클라이언트를 호출마다 생성** | `adapters/storage_client.py:71,95` | 실측 **2.5ms → 0.13ms** (약 20배) |
| **LLM 재시도·타임아웃 없음** | `services/question_service.py:40` | 429 하나에 학생이 "다시 시도" 연타 → 부하 자가증폭 |
| 레이트리밋 없음 | — | 크레딧 소진·재시도 폭주에 무방비 |
| 단일 인스턴스, 롤백 없음 | `DEPLOYMENT.md:108` | 컨테이너 정지 = 전면 장애 |
| **서버에서 `docker build`** | `.github/workflows/deploy-backend.yml` | 행사 중 배포 시 메모리 스파이크 + 다운타임 |

## 5. 인프라 확장 방안

### 5.1 선택지 비교

| 방안 | 비용(월) | 작업량 | 이번 행사 적합성 |
|---|---|---|---|
| **A. 수직 확장** (플랜 업 + 워커 증설) | $84 | 1시간 | ✅ **권장** |
| **B. Lightsail 2대 + LB** | $84×2 + $18 | 반나절 | 🟡 이중화가 꼭 필요하면 |
| **C. EC2 + ALB 전환** | 유사 | 2~3일 | ❌ 행사 전에는 비권장 |

### 5.2 A안 — 수직 확장 (권장)

Lightsail General Purpose 플랜 (Linux, dual-stack, 2026-08-08 기준):

| 월 요금 | RAM | vCPU | SSD | 전송 |
|---|---|---|---|---|
| $12 | 2 GB | 2 | 60 GB | 3 TB | ← 현재 |
| $24 | 4 GB | 2 | 80 GB | 4 TB |
| $44 | 8 GB | 2 | 160 GB | 5 TB |
| **$84** | **16 GB** | **4** | 320 GB | 6 TB | ← 권장 |

**vCPU 4개가 나오는 첫 플랜이 16GB/$84다.** 행사 2~3일치로 환산하면 약 $8이므로
비용은 사실상 고려 대상이 아니다. 행사 후 작은 플랜으로 되돌린다.

절차는 기존 문서(`2026-06-27-backend-deploy-lightsail-supabase.md:278`)에 이미 있다.

```
스냅샷 생성 → 더 큰 플랜으로 새 인스턴스 생성 → 고정 IP 재할당
```

함께 적용할 것:

```dockerfile
# backend/Dockerfile — 워커 4개
CMD ["uv", "run", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "4"]
```

```python
# app/main.py:52
await db_pool.connect(min_size=5, max_size=20)
```

⚠️ **워커를 늘리면 카드 워커가 프로세스마다 중복 기동된다**(`app/main.py:57`).
`CARD_WORKER_ENABLED=false`로 웹 컨테이너에서 끄고, 워커는 별도 컨테이너 1개로 분리한다.

⚠️ **DB 커넥션 총량 = 워커 수 × 풀 크기**다. 4 × 20 = 80. Supabase 직접 연결
한도를 넘지 않는지 확인하고, 넘으면 Supavisor **세션 모드**(트랜잭션 모드 `:6543`이
아니라)를 쓴다. 트랜잭션 풀러를 피해야 하는 이유는 기존 문서 `:71`에 정리돼 있다.

### 5.3 B안 — Lightsail 2대 + 로드밸런서

**앱은 이미 stateless라 수평 확장이 가능하다.** 확인한 근거:

- 인증이 JWT라 서버 측 세션이 없다 (`core/security.py`)
- 인메모리 캐시·세션 저장소가 없다
- 업로드는 S3로 직행한다 (`adapters/storage_client.py`)
- DB는 Supabase를 공유한다
- 카드 워커는 `FOR UPDATE SKIP LOCKED` 설계라 다중 인스턴스에서도 안전하다
  (`backend-design.md:113`) — 다만 운영 단순화를 위해 **1대에서만** 돌린다

구성 변경:

| 항목 | 변경 |
|---|---|
| TLS 종료 | Caddy → **로드밸런서**($18/월, 인증서 관리 통합) |
| `Caddyfile` | 제거. app 컨테이너를 80으로 노출 |
| CD 워크플로 | 2대에 순차 배포 (한 대씩 → 무중단 배포도 가능해짐) |
| `IMAGE_CONCURRENCY` | 인스턴스 수로 나눠 설정 (총량이 2배가 되지 않도록) |
| DB 풀 | 인스턴스 × 워커 × 풀 크기가 한도를 넘지 않게 재계산 |

이중화가 필요하면 이 방안이 맞다. 단, **B안을 택해도 §2·§3의 문제는 그대로 남는다.**

### 5.4 C안 — EC2 전환 (행사 전에는 하지 말 것)

전환 자체는 가능하다.

1. Lightsail 스냅샷 → **Export to Amazon EC2** → AMI로 인스턴스 기동, 또는
2. EC2를 새로 만들고 저장소 clone + `.env` 배치 후 `docker compose` (이 프로젝트는
   코드가 전부 git + Docker라 **재구축이 export보다 빠르고 깨끗하다**)

바뀌는 것: 고정 IP(EIP), 방화벽 → 보안그룹, DNS A/AAAA, GitHub Secrets(`SSH_HOST`).

**하지만 행사 전에는 권하지 않는다.**

- Lightsail은 EC2를 감싼 것이라 **성능상 얻는 게 사실상 없다.** 같은 돈이면 같은 성능이다.
- 결정적 함정: **Supabase 직접 연결(`db.<ref>.supabase.co:5432`)은 IPv6 경로를 쓴다**
  (기존 문서 `:31`). EC2로 옮기면 **VPC 서브넷에 IPv6 CIDR을 직접 할당**해야 하고,
  누락하면 배포 직후 DB 연결 실패로 **API 전체가 죽는다.** CD에 롤백 단계도 없다.
- 얻는 것(오토스케일링, 다양한 인스턴스 타입)은 2일짜리 행사에서 쓸 일이 없다.

→ **행사 후 상시 서비스로 전환할 때 검토한다.**

## 6. 부하 테스트 방법

설계서 체크리스트(`backend-design.md:584`)에 있으나 아직 실시하지 않았다.

### 6.1 도구

시나리오(로그인 → 생성 → 저장 → 완료 → 부스)를 재현해야 하므로 **k6**를 쓴다.
`wrk`·`ab`는 단일 URL 반복이라 이 목적에 맞지 않는다.

```bash
brew install k6
```

시나리오는 학생 1명의 전체 여정(가입 → 사진 → 생성 3회 → 저장 10회 → 완료 → 프로필 →
부스 인증)을 한 반복으로 잡고, **초당 여정 시작 수**로 부하를 조절한다.
`10,000명 / 18,000초 = 0.56 여정/s`가 평균, 그 3배가 스파이크 목표다.

> 스크립트는 아직 작성하지 않았다 (2026-08-08 시점).

### 6.2 반드시 지킬 것

| 원칙 | 이유 |
|---|---|
| **운영 DB에 쏘지 않는다** | 가짜 학생 수천 건이 관리자 목록·좌석표·집계를 오염시킨다 |
| **LLM 호출을 실제로 태우지 않는다** | 1회 완주에 학생당 $0.01~0.02. 1,000 VU면 실제 돈이 나간다 |
| **정리 경로를 먼저 준비한다** | 테스트 후 `POST /api/admin/students/bulk-delete`로 회수 |

권장 환경 조합:

1. **스테이징 Supabase 프로젝트**를 따로 만들고 마이그레이션 0001~0008을 적용한다.
2. 앱은 **행사용과 같은 플랜의 Lightsail 인스턴스**에 띄운다
   (로컬 맥에서 재면 CPU가 달라 의미가 없다).
3. `AI_CHAT_BASE_URL`을 **로컬 스텁 서버**로 돌려 LLM 과금을 차단한다
   (지연만 흉내내면 충분하다 — `SKIP_LLM=1`로 아예 건너뛸 수도 있다).
4. 진행 중인 `kind='test'` 설계(`superpowers/specs/2026-08-08-guest-and-test-accounts-design.md`)가
   반영되면, 테스트 계정을 그 종류로 만들어 관리자 화면에서 자동 격리한다.

### 6.3 목표 수치

| 지표 | 목표 |
|---|---|
| 지속 부하 | **100 req/s** (예상 피크) |
| 스파이크 | **300 req/s** (피크 3배) |
| LLM 제외 API p95 | < 800ms |
| 오류율 | < 1% |
| 인스턴스 메모리 | 최대치의 70% 이하 |

`docker stats`와 `htop`으로 컨테이너 메모리·CPU를 동시에 관찰한다.
사진 업로드 동시성에서 메모리가 튀는지가 핵심 관찰 포인트다.

## 7. 실행 계획

### 7.1 먼저 결정할 것 — 카드는 행사 후 야간 배치로

이 결정 하나로 §2의 문제 절반이 사라진다.

| | 실시간 발급 | **야간 배치 (권장)** |
|---|---|---|
| 필요 처리량 | 1.11 img/s | 8시간 배치 시 **0.69 img/s** |
| 현재 동시성 10으로 | 부족 (45%) | 거의 충분 |
| 실시간 부하와 경합 | 있음 | 없음 |
| 실패 시 | 학생 앞에서 터짐 | 재시도 여유 있음 |

프론트도 이미 이 전제로 쓰여 있다 — `frontend/lib/api.ts:524`:
*"탐험대원증 이름·카드는 이후(한마당)에 생성·공개한다"*

### 7.2 P0 — 행사 전 필수

| # | 작업 | 예상 |
|---|---|---|
| 1 | Supabase **Free → Pro** ($25) | 30분 |
| 2 | Lightsail **2GB/2vCPU → 16GB/4vCPU** ($84, 행사 후 축소) | 1시간 |
| 3 | `--workers 4` + 카드 워커 컨테이너 분리 | 30분 |
| 4 | DB 풀 상향 `connect(min_size=5, max_size=20)` + 커넥션 총량 검산 | 30분 |
| 5 | LLM 호출에 타임아웃·재시도(429/5xx)·동시성 상한 — 이미지 쪽 `_run_with_image_retries`(`adapters/ai_client.py:344`) 패턴 이식 | 2시간 |
| 6 | **카드 파이프라인 연결** — `ops.jobs` 마이그레이션 + `CardRepository` + 워커 + `/api/cards/*` | **3~5일** |
| 7 | 부하 테스트 (§6) | 1일 |
| 8 | 행사 중 **배포 동결** + 이미지 GHCR 프리빌드 | 2시간 |
| 9 | OpenRouter 크레딧 선충전 — 최소 $3,500 (절감안 적용 시 $1,800) | — |

### 7.3 P1 — 여유가 되면

- 프로필 API DB 왕복 7회 → 1~2회 통합, 부스 목록·`retry_enabled` 인메모리 TTL 캐시
- S3 클라이언트를 lifespan 싱글톤으로 (실측 약 20배)
- 토큰·IP 단위 레이트리밋
- 업타임 모니터링 + 5xx 알림 (현재는 장애를 현장에서 육안으로 확인해야 한다)
