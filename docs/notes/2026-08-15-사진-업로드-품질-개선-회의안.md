## 1. 문제

학생이 사진을 올리기는 하는데, **본인 얼굴이 아니거나**(밈·캐릭터·친구·풍경)
**얼굴이어도 쓸 수 없는 상태**(어둡다·멀다·여러 명·가려짐)인 비율이 높다.

사진은 프로필 이미지가 아니라 **AI가 "28살의 너"를 그리는 원본 입력**이다
(`backend/app/core/prompts/image_prompt.py:15`). 사진 품질이 낮으면 카드 결과물 전체가 무너진다.

### 증상을 둘로 나눠야 한다

| 증상 | 기계가 잡나 | 대응 수단 |
|---|---|---|
| **얼굴이 아님** (밈·캐릭터·풍경) | **아니오** | 설득·유도·사람의 눈 |
| **얼굴인데 쓸 수 없음** (어둡다·작다·흐리다) | **예** | 픽셀 통계로 경고 |

**"얼굴이 아님"은 기계로 못 막는다.** 고해상도로 잘 찍은 캐릭터 일러스트는 어떤 안으로도 안 걸러진다.
회의에서 이걸 먼저 합의하고 기대치를 잡아야 한다.

## 2. 언제 사진을 요구할 것인가 ★

이번 정리의 핵심 주제. 후보는 세 지점이다.

### 현재 상태

```
회원가입(1/2)  →  사진(2/2)  →  탐험 브리핑  →  설문 Q1~9  →  카드 생성(행사 당일 공개)
   이름·비번          ↑ 지금 여기
   성별·동의
```

- 사진은 **가입 2단계**로 프레임돼 있다 (`signup/page.tsx:170` "탐험대 등록 · 1/2" → `signup/photo`)
- 백엔드는 **가입과 사진이 분리된 걸 전제**로 설계돼 있다
  (`routers/auth.py:30` — "사진은 가입 후 별도 엔드포인트로 올린다, `photo_key`는 처음엔 비어 있음")
- 사진 없이는 설문에 진입할 수 없다 (`flow.ts:103` `canAccess("explore") = hasPhoto`)

### 세 시점 비교

| | **A. 가입 폼 안** | **B. 가입 직후 (현재)** | **C. 설문 이후** |
|---|---|---|---|
| 학생의 몰입도 | **최저** | 낮음 | **최고** |
| 사진의 용도를 아는가 | 모름 | 모름 | **안다** (방금 자기 결과를 봄) |
| 미업로드 이탈 | 없음 | 없음 (관문) | **발생** |
| 구현 비용 | 중 (폼 상태 관리) | — (현행) | 중 (`flow.ts` 가드 재설계) |
| 예상 사진 품질 | **최악** | 나쁨 | **최고** |

**A (가입 폼 안) — 기각.**
가입 폼은 이미 이름·비번·성별·학교 4필드·동의로 무겁다. 여기에 카메라 실행까지 넣으면
폼 상태 유지가 까다로워지고, 무엇보다 **앱을 방금 연 사람에게 얼굴을 요구하는 지점**이라 동기가 최저다.
백엔드도 가입 API와 사진 업로드를 분리해 뒀으므로 굳이 합칠 이유가 없다.

**B (가입 직후 = 현재) — 완주율은 최고, 품질은 나쁨.**
관문이라 미업로드가 구조적으로 없다. 대신 학생은 **아직 아무것도 투자하지 않았고,
사진이 뭐에 쓰이는지도 모른다.** 밈 업로드의 온상이 여기다.

**C (설문 이후) — 품질은 최고, 완주율이 위험.**
9문항을 푼 직후라 몰입도가 최고조이고, 자기 페르소나 결과를 막 본 상태라
"이 카드에 네 얼굴을 넣자"가 자연스럽다. 대신 **사진 없이 이탈하는 학생이 새로 생긴다** —
지금은 관문이라 그 경우가 없는데, C로 옮기면 설문만 하고 사라지는 학생이 카드 제작 파이프라인에 섞인다.

### 결론 — B 유지 + C에 확인 단계 추가 (하이브리드)

**둘 중 하나를 고르는 문제가 아니다. 요구는 B에서 하고, 교체 기회를 C에서 준다.**

```
회원가입  →  사진 [필수, 현행 유지]  →  설문 Q1~9  →  [NEW] 사진 확인·교체  →  카드 생성
                    ↑                                        ↑
             완주율 보장 (관문)                    품질 회수 (몰입도 최고 지점)
```

- **B 유지** → 미업로드 이탈 리스크 **0**. 지금 구조를 안 건드린다.
- **C에 확인 단계 추가** → "네 대원증에 이 사진이 들어가. 이대로 할까?" + 현재 사진 미리보기 + **다시 올리기** 버튼

**왜 이게 최선인가:**
1. **자기교정 기회를 API 없이 만드는 유일한 방법.** 제약으로 안 D(AI 미리보기)가 빠지면서
   학생이 스스로 고칠 계기가 사라졌는데, 이 단계가 그 자리를 메운다.
   밈을 올린 학생도 이 시점엔 카드에 애착이 생겨서 **스스로 바꾼다.**
2. **이미 있는 기능을 살린다.** 프로필 화면에 사진 수정이 이미 있는데
   (`app/(tabs)/profile/[id]/page.tsx:111`), **아무도 그리로 가지 않는다.** 유도 동선이 없어서다.
3. **완주율 리스크가 없다.** 사진은 이미 받았으므로, 이 단계를 건너뛰어도 잃는 게 없다.
   → **건너뛰기 허용**으로 만들어 이탈을 0으로 유지한다.
4. **비용이 낮다.** 프론트 화면 하나. `flow.ts`에 화면 하나 추가하면 되고, 가드 재설계가 필요 없다.

**리스크**: 단계가 하나 늘어 설문 완료 직후 이탈이 생길 수 있다. → 건너뛰기를 명확히 노출해 완화.

**대안 (더 가벼운 형태)**: 별도 화면 없이 `pending-card` 화면에 현재 사진과 "사진 바꾸기" 링크를 얹는다.
비용이 더 낮지만 주목도도 낮다. 먼저 이걸로 시작해 보는 것도 방법.

## 3. 원인 (코드 근거)

### 원인 1 — 문구가 보상이 아니라 부담을 말한다

`frontend/app/signup/photo/page.tsx:129-138`
> **"대원증에 붙일 사진을 담아줘"** / "한마당에서 **친구들에게 보여줄** 너만의 표식이야"

10대가 읽는 건 *"내 얼굴이 배지에 박히고 친구들이 본다"* — 보상이 아니라 **리스크**다.
이 프레임에서는 밈 사진이 오히려 합리적이다.
진짜 보상("네 얼굴로 28살의 너를 그려준다")은 **화면 어디에도 안 적혀 있다.**

### 원인 2 — 보상이 행사 당일까지 안 보인다

`frontend/app/explore/pending-card/page.tsx:13`
> `// 탐험대원증 이름·카드는 한마당에서 공개하므로, 여기서는 "만들어지는 중"만 보여준다.`

앱 안에서 결과를 한 번도 못 본다. 2절의 확인 단계가 이 간극을 일부 메운다.

### 원인 3 — 갤러리 경로엔 크롭이 없고, 미리보기가 실제와 다르다

- `page.tsx:66-71` `handleFileChange` → `applySelectedFile()` 직행. **`CropStep`을 건너뛴다.**
  카메라는 원형 가이드 + 720×720 크롭을 거치지만, **갤러리는 원본 그대로 업로드**된다.
- `page.tsx:160-161` 미리보기는 `bg-cover bg-center`로 가운데를 원형으로 잘라 보여준다.
  → 학생은 "얼굴 잘 들어갔네" 하고 확인하지만 **AI는 잘리지 않은 단체사진 원본을 받는다.**
- 프로필 사진 수정(`profile/[id]/page.tsx:111`)도 동일하게 크롭이 없다.

### 원인 4 — 이미 있는 검증 도구를 학생 사진 경로에서만 안 쓴다

`backend/app/core/images.py`의 `inspect_image()`(Pillow, 디코드 무결성 + 해상도)는
*AI 생성 이미지* 검사에만 쓰이고, **학생 업로드 경로(`auth_service.py:212`)는 거치지 않는다.**
라우터도 MIME 타입과 10MB만 본다 — **40×40 아이콘도, 손상 파일도 통과한다.**

| 안 | 내용 | 비용 |
|---|---|---|
| **T** | **설문 이후 사진 확인·교체 단계 추가** (건너뛰기 허용) | **S~M** |

### 동기 — 올리기 전에 설득한다

| 안 | 내용 | 비용 | 비고 |
|---|---|---|---|
| **A** | 문구 재프레임 + **완성 카드 예시를 실제로 보여준다** | S | 아래 상세 |
| **K** | **"사진을 안 올리면 캐릭터로 대체된다"를 미리 알린다** | S~M | 아래 상세. **현행 폴백 결함도 같이 고친다** |
| **J** | 좋은 예 / 나쁜 예 O·X 썸네일 4장 | S | **"캐릭터는 안 된다"를 명시적으로 전달하는 유일한 안** |
| **H** | 개인정보 안심 문구 (열람 범위 명시) | S | 사진은 영구 보관이라 **"지워진다"는 약속 불가** |

**안 A 상세 — 말로 설명하지 말고 결과를 보여준다.**
"네 얼굴로 28살의 너를 그려줄게"라고 **쓰는 것**과, 완성된 대원증 카드를 **보여주는 것**은 설득력이 다르다.
업로드 화면에 **운영진 얼굴로 미리 만들어 둔 완성 카드 1~2장**을 올린다.
얼굴 사진 → 카드로 이어지는 흐름을 눈으로 보면 "왜 진짜 얼굴이 필요한지"에 설명이 필요 없어진다.
예시는 **미리 1회 생성해 정적 에셋으로 박아둔다** — 런타임 API 호출 없음.
평균 수준의 결과물을 고를 것. 예시가 실제보다 좋으면 기대 불일치가 생긴다.

**안 K 상세 — "안 올리면 이렇게 나가"를 미리 보여준다.**

지금 사진 없는 학생의 카드가 어떻게 나오는지 확인해 보면 이건 유도 문구 이전에 **결함**이다.

```
persona_pipeline.py:29-31
  if photo is not None:  → ai.edit_image(...)   # 본인 얼굴 기반
  else:                  → ai.generate_image(...) # 사진 없이 프롬프트만으로 생성
```

프롬프트는 여전히 *"the SAME person as the input photo"*(`image_prompt.py:15`)인데
참조할 사진이 없으니, AI는 **아무 상관 없는 낯선 사람의 실사 얼굴**을 그린다.
→ **사진 없는 학생의 대원증에는 모르는 사람 얼굴이 박혀 나간다.** 캐릭터보다 나쁘다.

**할 일 두 가지:**

**1. 폴백을 낯선 사람 실사 얼굴 → 캐릭터 얼굴로 바꾼다.** 구현 방식은 두 가지.

| | **(a) 정적 캐릭터 에셋** | **(b) 캐릭터 프롬프트로 생성** |
|---|---|---|
| 방식 | 미리 만든 캐릭터 이미지 몇 종 중 하나를 붙인다 | `photo is None`일 때 **다른 프롬프트**로 `generate_image` |
| AI 호출 | **없음** | 있음 (카드 파이프라인은 어차피 호출 중) |
| 결과 예측 | **가능** — 학생에게 실물을 그대로 보여줄 수 있다 | 불가 — 매번 달라진다 |
| 다양성 | 낮음 (몇 종 반복) | 높음 |
| 비용 | 0 | 기존과 동일 |

**(a) 추천.** 할 일 2번(“안 올리면 이게 들어가”를 미리 보여주기)이 성립하려면
**결과가 예측 가능해야** 한다. (b)는 매번 달라져서 미리 보여줄 수가 없다.
캐릭터가 몇 종뿐이라 겹치는 건 오히려 **"나만의 것이 아니다"** 는 신호가 되어 이 안에 유리하다.

현재 코드는 프롬프트 분기 없이 `generate_image`로만 빠지므로(`persona_pipeline.py:31`),
어느 쪽이든 `_portrait`의 else 분기를 손봐야 한다.

**2. 업로드 화면에서 미리 알린다** — "사진을 안 올리면 네 대원증엔 이 캐릭터가 들어가" + 캐릭터 실물.
안 A의 실사 카드 예시와 **나란히** 놓으면 대비가 선명해진다.

**설계 주의 — 캐릭터를 선택지로 주면 안 된다.**
- "캐릭터로 할래" 버튼을 만들면 **쉬운 탈출구**가 되어 사진 비율이 오히려 떨어진다.
  캐릭터는 어디까지나 *"안 하면 이렇게 된다"* 는 **결과**로만 노출한다.
- **캐릭터를 멋지게 만들면 안 된다.** 10대 중엔 캐릭터를 더 선호하는 학생이 분명히 있다.
  기본 실루엣·단색 아바타 수준으로 **의도적으로 밋밋하게** 만든다.
  "내 카드만 밋밋하네"가 이 안의 작동 원리다.

### 유도 — 올리는 순간에 좁힌다

| 안 | 내용 | 비용 | 비고 |
|---|---|---|---|
| **F** | "사진 촬영"을 기본 버튼으로, "갤러리"는 작은 링크로 | S | **밈은 거의 전부 갤러리에서 온다.** 얼굴 검출 없이 "얼굴 아님"을 줄이는 가장 구조적인 수단 |
| **B** | 갤러리에도 `CropStep` 적용 — 미리보기 = 실제 업로드 | S | **자동 중앙 크롭 금지, 학생이 직접 영역 선택** (아래 참고) |
| **I** | 픽셀 통계(해상도·밝기·선명도·단색)로 **경고만** | S~M | **B가 전제** — B가 있으면 모든 사진이 canvas를 거쳐 거의 공짜 |
| **I-a** | 백엔드 `attach_photo`에 `inspect_image()` 연결 | S | 단독 도입 가능. Pillow 이미 의존성 |

**안 B 상세 — 자동 중앙 크롭으로 때우지 말 것.**
가운데를 기계적으로 자르면 얼굴이 중앙에 없는 사진(단체사진 구석, 치우친 셀카)에서 **오히려 얼굴이 잘려 나간다.**
`CropStep`은 이미 드래그·핀치 줌·줌 슬라이더로 영역 선택을 지원하므로(`CameraCapture.tsx:277-482`)
갤러리 경로에서도 이 UI를 그대로 쓴다. 학생이 "얼굴을 원 안에 맞추는" 행위 자체가 좋은 사진을 고르게 만드는 유도 장치다.

**안 I 한계**: **"얼굴이 아님"은 전혀 못 잡는다.** 고해상도 캐릭터 일러스트는 100% 통과한다.
그리고 **막지 않고 경고만 한다** — 어두운 데서 찍은 진짜 학생이 갇히면 안 된다.

### 사후 — 이미 올라온 사진

| 안 | 내용 | 비용 | 비고 |
|---|---|---|---|
| **G1** | 관리자 **사진 그리드 뷰** (썸네일 격자) | M | 밈은 격자로 보면 한눈에 튄다. **유일한 측정 수단** |
| **G2** | 재촬영 요청 발송 (학생 앱 유도) | L | G1 + 현장 호출로 대체 가능 |

**G1이 왜 중요한가**: 지금은 문제 규모를 측정할 방법이 **아예 없다.**
이 뷰가 생겨야 "몇 %가 문제인지" 처음 알게 되고, 다른 안의 전후 비교가 가능해진다.
기반은 이미 있다 — 사진 조회(`console/StudentListView.tsx`), 다건 서명(`create_signed_urls()`).

## 5. 추천 순서

| 순서 | 안 | 이유 |
|---|---|---|
| **0차 · 측정** | **G1** | 뭘 고치든 효과를 확인할 수단이 먼저 있어야 한다. 없으면 전부 감으로 하는 일이 된다 |
| **1차 · 즉시** | **A + K + J + F + B** | 대부분 프론트만. A·K는 "얼굴 카드 vs 밋밋한 캐릭터" 대비로 동기를 만들고, F·B가 유도를 좁힌다. **K의 폴백 수정은 별개로 어차피 고쳐야 할 결함** |
| **2차** | **T** | 시점 하이브리드. 자기교정 기회를 API 없이 만드는 유일한 수단 |
| **3차** | **I-a → I** | I-a는 서버 방어선으로 단독 도입 가능. I는 B가 깔린 뒤라야 저렴 |
| **조건부** | **H · G2** | H는 거부 이유가 "개인정보 걱정"일 때. G2는 G1 + 현장 대응으로 부족할 때 |

## 6. 제약으로 제외된 안

| 안 | 내용 | 제외 사유 |
|---|---|---|
| **D** | 업로드 직후 AI 초상 미리보기 → 자기교정 | 런타임 이미지 생성 API 호출 금지 |
| **E** | 자동 얼굴 검출 게이트 | 얼굴 검출 비현실적. 오판정 시 진짜 학생이 갇힘 |

**제외의 대가**: **"얼굴이 아님"을 자동으로 걸러낼 수단이 하나도 남지 않았다.**
남은 건 설득(A·J·H), 유도(F·T), 사람의 눈(G1·G2)뿐이다.

## 7. 회의에서 결정할 것

1. **사진 요청 시점을 하이브리드(B 유지 + C 확인 단계)로 갈 것인가?** — 2절
2. **학생들이 얼굴을 안 올리는 진짜 이유는?** (쪽팔림 / 개인정보 걱정 / 장난 / 좋은 사진 없음)
   → 주력이 A·J인지 H인지 F인지가 갈린다. **현재는 추측이다.**
3. **"얼굴이 아닌 사진은 기계로 못 막는다"를 받아들이는가?** → 받아들이면 G1이 필수가 된다
4. **행사까지 남은 기간은?** → 백엔드를 건드리는 안(T·G1·G2·I-a) 가능 여부
5. **G1의 사진 검토를 누가, 언제 하는가?**
