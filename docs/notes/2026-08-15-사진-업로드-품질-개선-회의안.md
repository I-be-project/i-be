# 사진 업로드 품질 개선 — 회의안

작성일: 2026-08-15
상태: **논의용 초안 (구현 전)**

## 제약 (확정)

이 두 가지는 논의 대상이 아니라 **전제**다.

| 제약 | 영향 |
|---|---|
| **런타임 AI/이미지 생성 API 호출 금지** | 업로드 시점에 초상을 만들어 보여주는 안은 불가 |
| **얼굴 검출(자동 판정)은 비현실적** | "얼굴인지"를 기계가 판단하는 안은 불가 |

→ 제외된 안과 그 이유는 8절에 남긴다.

## 1. 문제

학생이 사진을 올리기는 하는데, **본인 얼굴이 아니거나**(밈·캐릭터·친구·풍경)
**얼굴이어도 쓸 수 없는 상태**(너무 어둡다·멀다·여러 명·가려짐)인 비율이 높다.

사진은 프로필 이미지가 아니라 **AI가 "28살의 너"를 그리는 원본 입력**이다
(`backend/app/core/prompts/image_prompt.py:15` — *"the SAME person as the input photo, depicted at exactly 28 years old"*).
따라서 사진 품질이 낮으면 카드 결과물 전체가 무너진다. UX 문제가 아니라 **핵심 산출물의 품질 문제**다.

### 증상을 둘로 나눠야 한다

제약(얼굴 검출 불가) 때문에 두 증상의 대응 수단이 완전히 다르다.

| 증상 | 기계가 잡을 수 있나 | 대응 수단 |
|---|---|---|
| **얼굴이 아님** (밈·캐릭터·풍경) | **아니오** — 얼굴 검출이 있어야만 가능 | 설득·유도·사람 (안 A·J·F·C·G) |
| **얼굴인데 쓸 수 없음** (어둡다·작다·흐리다) | **예** — 픽셀 통계로 가능 | 자동 경고 (안 B·I) |

**"얼굴이 아님"은 기계로 못 막는다는 걸 회의에서 합의하고 가야 한다.**
고해상도로 잘 찍은 캐릭터 일러스트는 아래 어떤 안으로도 걸러지지 않는다.
이 부분은 **동기 설계와 사람의 눈**으로만 줄일 수 있다.

## 2. 코드에서 확인한 원인

### 원인 1 — 요청 시점과 보상 시점이 최대로 떨어져 있다

| | 시점 | 그때 학생의 상태 |
|---|---|---|
| **사진 요청** | 가입 2단계 (`flow.ts:33-40` 순서상 맨 앞) | 앱 들어온 지 1분, 아무것도 투자 안 함 |
| **보상 공개** | 한마당 행사 당일, 오프라인 | 며칠 뒤. 앱 안에서는 결과를 한 번도 못 봄 |

`frontend/app/explore/pending-card/page.tsx:13`
> `// 탐험대원증 이름·카드는 한마당에서 공개하므로, 여기서는 "만들어지는 중"만 보여준다.`

학생은 **몰입도 0인 상태에서 얼굴을 요구받고**, 그 대가는 **앱 안에서 볼 수 없다**.
설문 9문항을 다 푼 뒤라면 같은 사람이 훨씬 잘 응한다.

### 원인 2 — 문구가 보상이 아니라 부담을 말한다

`frontend/app/signup/photo/page.tsx:129-138` 현재 문구:

> **"대원증에 붙일 사진을 담아줘"**
> "별빛이 내린 밤, 탐험대원증에 네 얼굴이 빛날 거야. **한마당에서 친구들에게 보여줄** 너만의 표식이야."

10대가 읽는 건 *"내 얼굴이 배지에 박히고 친구들이 본다"* — 보상이 아니라 **리스크**다.
이 프레임에서는 밈 사진이 오히려 합리적인 선택이 된다.
정작 진짜 보상("네 얼굴로 28살의 너를 그려준다")은 **화면 어디에도 안 적혀 있다.**

### 원인 3 — 갤러리 경로엔 크롭이 없고, 미리보기가 실제와 다르다

- `page.tsx:66-71` `handleFileChange` → `applySelectedFile()` 직행. **`CropStep`을 건너뛴다.**
  카메라는 원형 가이드 + 720×720 크롭을 거치지만, **갤러리는 원본 그대로 업로드**된다.
- `page.tsx:160-161` 미리보기는 `bg-cover bg-center`로 **가운데를 원형으로 잘라 보여준다.**
  → 학생은 "얼굴 잘 들어갔네" 하고 확인하지만, **AI가 받는 건 잘리지 않은 단체사진 원본**이다.
  **미리보기가 사실과 다르다.**
- 프로필 화면의 사진 수정(`app/(tabs)/profile/[id]/page.tsx:111`)도 **동일하게 크롭이 없다.**

### 원인 4 — 이미 있는 검증 도구를 학생 사진 경로에서만 안 쓴다

`backend/app/core/images.py`의 `inspect_image()`는 Pillow로 **디코드 무결성 + 해상도**를 확인해 돌려준다.
그런데 이건 *AI 생성 이미지* 검사에만 쓰이고, **학생 업로드 경로는 거치지 않는다.**

`backend/app/services/auth_service.py:212`
```
photo_key = await self._storage.upload_photo(path, data, content_type=content_type)
```
→ 바이트를 그대로 S3에 넣는다. 라우터(`students.py:32-46`)도 MIME 타입과 10MB만 본다.

**40×40 아이콘도, 잘린 손상 파일도 통과한다.**
Pillow는 이미 의존성이고 함수도 이미 있다 — **한 줄 호출로 해상도 검사가 생긴다.**

## 3. 안 — 그룹 1: 동기 (올리기 전에 설득한다)

> 비용: **S** = 프론트 문구/로직만 · **M** = 구조 변경 또는 백엔드 소폭 · **L** = 백엔드 + 관리자 UI

### 안 A. 문구를 "보상"으로 다시 쓴다 — S

"대원증에 붙일 사진" → **"네 얼굴로 28살의 너를 그려줄게"** 로 프레임 전환.
비포/애프터 예시 한 쌍을 같이 노출해 결과물을 눈으로 보여준다.

- **근거**: 지금은 보상이 문자 그대로 안 적혀 있다. 알리기만 해도 "왜 진짜 얼굴이어야 하는지"가 성립한다.
- **제약 준수**: 예시 이미지는 **운영진 얼굴로 미리 1회 생성해 정적 에셋으로 박아둔다.** 런타임 API 호출 없음.
- **리스크**: 예시가 실제 결과보다 좋으면 기대 불일치. 평균 수준의 결과물을 고를 것.

### 안 J. 좋은 예 / 나쁜 예를 나란히 보여준다 — S

업로드 화면에 O/X 썸네일 4장. 정면 클로즈업(O) / 단체사진(X) / 어두운 사진(X) / 캐릭터(X).

- **근거**: **규범을 보여주는 게 규칙을 쓰는 것보다 강하다.** 지금 학생은 "어떤 사진이 맞는 사진인지" 본 적이 없다. 특히 "캐릭터는 안 된다"를 유일하게 명시적으로 전달하는 안이다.
- **리스크**: 거의 없음. 화면이 조금 길어진다.
- **비고**: 얼굴 검출 없이 "얼굴이 아님" 증상을 건드리는 **가장 싼 수단**.

### 안 H. 개인정보 안심 문구를 명시한다 — S

사진이 **어디에 쓰이고 누가 보는지**를 화면에서 분명히 말한다.

- **근거**: 거부 이유가 "쪽팔림"이 아니라 "걱정"인 학생에게는 이게 유일한 해법이다.
- **주의**: 사진은 영구 보관 정책이므로 **"나중에 지워진다"는 약속은 할 수 없다.** 대신 열람 범위를 정확히 쓴다.
- **채택 조건**: 5절 질문 1의 답이 "개인정보 걱정"일 때만 주력이 된다.

## 4. 안 — 그룹 2: 유도 (올리는 순간에 좁힌다)

### 안 F. 갤러리를 2차 선택지로 내린다 — S

"사진 촬영"을 기본(큰 버튼)으로, "갤러리에서 선택"은 작은 텍스트 링크로.

- **근거**: **밈·캐릭터는 거의 전부 갤러리에서 온다.** 지금은 두 버튼이 동등한 크기(`page.tsx:177-196`)라 갤러리가 똑같이 매력적이다. 방금 찍은 사진은 정의상 본인 얼굴일 확률이 훨씬 높다.
- **리스크**: 카메라 없는 기기·권한 거부 등 정당한 갤러리 사용 방해. 폴백은 이미 구현돼 있음(`CameraCapture`의 `onFallback`).
- **비고**: 얼굴 검출 없이 "얼굴이 아님"을 줄이는 **가장 구조적인 수단**. 비용 대비 효과가 가장 좋을 수 있다.

### 안 B. 갤러리에도 크롭을 적용한다 — S

`CropStep`을 갤러리 경로에서 재사용해 **미리보기와 실제 업로드를 일치**시킨다. 프로필 수정도 동일 적용.

- **근거**: "얼굴이긴 한데 쓸 수 없다"의 상당 부분이 여기서 나온다. 단체사진·전신샷을 구조적으로 막는다.
- **리스크**: 단계가 하나 늘어 이탈 가능성. 다만 카메라 경로는 이미 이 단계를 거치는 검증된 UX다.
- **비고**: **안 I의 전제 조건이기도 하다** — 아래 참고.

### 안 I. 픽셀 통계로 경고만 한다 — S~M

업로드 직전에 **얼굴을 찾지 않고** 계산할 수 있는 것만 보고, 막지 않고 **경고만** 한다.

| 검사 | 방법 | 잡히는 것 |
|---|---|---|
| 해상도 | `inspect_image()` (이미 존재) 또는 클라이언트 | 밈·스크린샷·웹 이미지 상당수 |
| 평균 밝기 | Canvas `getImageData` → 휘도 평균 | 너무 어두운 사진 |
| 선명도 | Laplacian 분산 | 흔들린·흐린 사진 |
| 단색 여부 | 색 분산 | 검은 화면, 빈 이미지 |

- **제약 준수**: **전부 순수 계산이다.** 얼굴 검출 아님, API 호출 아님, 외부 라이브러리 없음.
- **구현 비용이 B에 달려 있다**: B를 채택하면 **모든 사진이 이미 canvas를 거치므로** 통계 계산이 거의 공짜다. B 없이 단독 도입하면 canvas 파이프라인을 새로 만들어야 해서 비싸진다.
- **한계 (반드시 합의할 것)**: **"얼굴이 아님"은 전혀 못 잡는다.** 고해상도로 잘 찍은 캐릭터 일러스트는 100% 통과한다. 이 안은 오직 "쓸 수 없는 사진"만 담당한다.
- **막지 않는 이유**: 어두운 조명에서 찍은 진짜 학생이 갇히면 안 된다. "이 사진 좀 어두워. 이대로 할까?" + 계속하기 버튼으로.

### 안 I-a. 백엔드에 `inspect_image()`를 연결한다 — S (독립 실행 가능)

`attach_photo`에서 `inspect_image()`를 호출해 **손상 파일·비정상 해상도를 거른다.**

- **근거**: 원인 4. 이미 있는 함수를 안 쓰고 있을 뿐이다.
- **비용**: 매우 낮음. Pillow는 이미 의존성.
- **비고**: 안 I(프론트 경고)와 무관하게 **서버 방어선으로 단독 도입 가능.** 다만 이것만으로는 학생에게 아무 안내도 안 간다.

## 5. 안 — 그룹 3: 구조 (언제 요청하는가)

### 안 C. 요청 시점을 설문 완료 직후로 옮긴다 — M

가입 2단계에서 빼고, 설문을 다 푼 뒤 **"이제 네 카드를 만들자"** 시점에 요청한다.

- **근거**: 원인 1에 대한 정면 대응. 9문항을 투자한 직후라 몰입도가 최고조이고, 사진의 용도가 그 자리에서 자명해진다.
- **리스크**: `flow.ts`의 화면 순서·진입 가드(`canAccess`) 재설계. **설문만 하고 사진 없이 이탈하는 학생이 새로 생긴다** — 지금은 사진이 관문이라 그 경우가 없다.
- **비고**: 안 A와 궁합이 가장 좋다. 요청 시점에서 "지금 만들 카드"를 바로 보여줄 수 있으므로.

## 6. 안 — 그룹 4: 사후 (이미 올라온 사진)

기계가 "얼굴 아님"을 못 잡는 이상, **결국 사람이 봐야 한다.** 이 그룹이 유일한 실질적 방어선이다.

### 안 G1. 관리자 사진 그리드 뷰 — M

관리자 화면에 **썸네일 격자**를 추가해 전체 사진을 한 화면에서 훑어본다.

- **근거**: 밈·캐릭터는 격자로 보면 **한눈에 튄다.** 수백 장도 몇 분이면 스캔된다.
- **부수 효과 — 이게 더 중요할 수 있다**: 지금은 문제 규모를 **측정할 방법이 아예 없다.** 이 뷰가 생기면 "몇 %가 문제인지" 처음으로 알게 되고, 다른 안의 효과도 전후 비교가 가능해진다.
- **기반**: 관리자 화면에 사진 조회는 이미 있다(`components/console/StudentListView.tsx`). 격자 레이아웃과 일괄 서명 URL이 신규 — 다건 서명은 `create_signed_urls()`가 이미 최적화돼 있다.
- **정렬 옵션(부가)**: 해상도가 작은 순으로 정렬하면 의심 사진이 앞으로 온다.

### 안 G2. 재촬영 요청 발송 — L

G1에서 문제 사진을 고르면 학생 앱이 사진 화면으로 유도된다.

- **근거**: 사람이 판단하므로 오판정이 없다.
- **리스크**: 백엔드(플래그·알림) + 학생 앱 유도 동선까지 작업량이 크다.
- **대안**: **G1만 하고 현장에서 운영진이 직접 부른다.** 행사 현장이라면 이게 더 빠를 수 있다 — G2 없이도 G1은 완결된 가치가 있다.

| 안 | 내용 | 제외 사유 |
|---|---|---|
| **D** | 업로드 직후 AI 초상 미리보기 생성 → 자기교정 유도 | **런타임 이미지 생성 API 호출 금지** 제약에 위배. 유일하게 학생이 스스로 품질을 올리는 구조였으나 불가. |
| **E** | 자동 얼굴 검출 게이트 | **얼굴 검출은 비현실적**이라는 판단. 브라우저 내장 검출은 지원이 불균일하고, 백엔드 검출은 오판정 시 진짜 학생이 갇히는 리스크가 크다. |

**제외의 대가**: 두 안이 빠지면서 **"얼굴이 아님"을 자동으로 걸러낼 수단이 하나도 남지 않았다.**
남은 대응은 설득(A·J·H), 유도(F·C), 사람의 눈(G1·G2)뿐이다. 이 한계를 전제로 기대치를 잡아야 한다.

## 9. 회의에서 결정할 것

1. **학생들이 얼굴을 안 올리는 진짜 이유가 무엇인가?**
   (쪽팔림 / 개인정보 걱정 / 그냥 장난 / 좋은 사진이 없음)
   → 주력이 A·J(설득)인지 H(안심)인지 F(차단)인지가 갈린다. **현재는 추측이고, 코드로는 알 수 없다.**
2. **"얼굴이 아닌 사진은 기계로 못 막는다"를 받아들이는가?**
   → 받아들인다면 G1(사람의 눈)이 선택이 아니라 필수가 된다.
3. **행사까지 남은 기간은?** → 백엔드를 건드리는 안(C·G1·G2·I-a)이 가능한지 결정한다.
4. **카드를 행사 당일에 공개한다는 원칙을 유지하는가?** → 유지하면 원인 1(보상 지연)은 구조적으로 못 없애고, 안 C로 완화만 가능하다.
5. **G1의 사진 검토를 누가, 언제 하는가?** → 사람이 필요한 유일한 안이라 인력 배정이 전제다.
