# 문서 체계 재설계 — 설계서

## 배경

모노레포 통합 이후 `docs/`가 평면 구조로 유지되면서 문서 체계가 실질적으로
작동하지 않게 됐다. 동시에, 개발 과정에서 발생한 문제와 그 해결 과정이
어디에도 남지 않아 같은 함정에 반복해서 빠지고 있다.

### 확인된 문제

**1. 수명이 다른 문서가 한 폴더에 섞여 있다**

`docs/` 평면에 설계서·배포 가이드·외부 전달용 매뉴얼·리스크 분석·디자인
시스템이 함께 있다. 설계서는 "그때 그렇게 정했다"는 불변 기록이고 배포
가이드는 "지금 이렇게 한다"는 항상 최신이어야 하는 문서인데, 둘이 같은
자리에 있으면 독자가 어느 쪽이 유효한지 판단할 수 없다.

**2. 선언한 컨벤션이 지켜지지 않는다**

- `docs/README.md`가 "이 프로젝트는 3개 레포로 나뉜다"라고 서술하지만
  이미 모노레포다.
- 같은 문서가 "결정 사항은 ADR로 분리하고 `→ ADR-NNNN`으로 참조"한다고
  선언하지만 ADR은 0개다.
- "문서 하단 변경 이력 표를 업데이트한다"는 규칙도 대부분 지켜지지 않는다.
- 실제 작업 이력인 `docs/superpowers/{specs,plans}` 20개 문서는 README에
  언급조차 없다.

지켜지지 않는 규칙은 문서 체계 전체의 신뢰를 깎는다. 다음 사람이 README를
믿지 않게 되면 README를 갱신할 이유도 사라진다.

**3. 파일 컨벤션 위반과 중복**

- `docs/backend-design.md` — 33KB 핵심 문서인데 날짜 접두사가 없다.
- 루트 `DEPLOYMENT.md`와 `docs/2026-06-27-backend-deploy-lightsail-supabase.md`가
  같은 주제를 다룬다.
- `frontend/docs/`에 `plan.md`·`dev-plan.md`와 별도 `superpowers/` 트리가
  살아 있어 루트 `docs/`와 이중화됐다.

**4. 이슈 → 해결 기록이 없다 (가장 큰 손실)**

356개 커밋 중 `fix:` 커밋이 다수인데, 커밋 메시지는 *무엇을* 고쳤는지만
남기고 *왜 그랬는지·어떻게 진단했는지·재발을 어떻게 막는지*는 소실된다.

실제 사례 — 아래 세 커밋은 모두 `frontend/app/admin/seating/page.tsx`
한 파일에서 같은 뿌리(비동기 요청 경합)로 발생했다.

```
4419ab5 fix: 좌석표 학교·반 전환 시 요청 경합으로 옛 응답이 최신 상태를 덮어씀
0cda678 fix: 학교 전환 시 진행 중이던 반 학생 요청을 무효화해 옛 명단이 남는 문제
519f25b fix: 학교 전환 무효화 시 반 학생 로딩 플래그도 함께 꺼서 무한 스켈레톤 방지
```

각 커밋 본문에는 상세한 원인 분석이 이미 담겨 있다. 부족한 것은 원인 분석이
아니라 **횡단 종합**이다. 커밋은 시간순 스트림이라 "이 화면의 세대 무효화
패턴을 세 번에 걸쳐 조금씩 깁고 있었다"는 사실을 드러내지 못한다.

401 처리 누락(`978be6c`·`3c4b277`·`87995e5`)도 같은 구조로 반복됐다. 관리자
화면에 새 `fetch`를 추가할 때마다 401 분기를 다시 빠뜨렸고, 그때마다 화면은
"학생이 없습니다" 같은 엉뚱한 빈 상태로 보였다.

## 목표

1. 문서를 열지 않고도 **아직 유효한지** 판단할 수 있게 한다.
2. 코드와 커밋만으로는 복원할 수 없는 지식을 남긴다.
3. 규칙을 지키는 비용을 낮춰서, 실제로 지켜지게 한다.

### 비목표

- 기존 문서 내용을 다시 쓰는 것. 이동과 최소 수정만 한다.
- 모든 `fix:` 커밋을 문서화하는 것.
- 문서 사이트 생성기(MkDocs 등) 도입.

## 설계

### 핵심 원칙 — 폴더를 수명(lifetime)으로 가른다

|  | 살아있는 문서 | 박제된 문서 |
|---|---|---|
| 성격 | 지금의 사실을 반영해야 한다 | 그 시점의 기록이다 |
| 내용이 틀렸을 때 | **고친다** | **고치지 않는다** (당시 판단이 그랬으므로) |
| 파일명 | 날짜 없음 | `YYYY-MM-DD-` 접두 |
| 예 | 배포 가이드, 아키텍처, API 명세 | 이슈 해결, 분석 리포트, 결정 기록 |

이 구분이 있으면 "이 문서 아직 유효한가?"에 **폴더 이름만으로** 답할 수 있다.

### 목표 디렉터리 구조

```
docs/
├─ README.md              문서 지도. 유일한 진입점
│
├─ guides/                [살아있음] 틀리면 고친다. 날짜 접두사 없음
│   ├─ architecture.md        시스템 구조
│   ├─ backend-design.md      백엔드 종합 설계
│   ├─ design-system.md       Voyage 디자인 시스템
│   ├─ admin-api.md           외부 전달용 관리자 API 매뉴얼
│   ├─ deployment.md          ← 루트 DEPLOYMENT.md 흡수
│   ├─ development.md         ← 루트 DEVELOPMENT.md 흡수
│   └─ operations.md          행사 운영 런북 (신규)
│
├─ issues/                [박제] 삽질·인프라 기록. 이 설계의 핵심
│   ├─ README.md              스크립트 생성 색인
│   └─ YYYY-MM-DD-<슬러그>.md
│
├─ notes/                 [박제] 분석·조사·결정 기록
│   └─ YYYY-MM-DD-<슬러그>.md
│
└─ superpowers/           자동 생성물. 현행 유지
    ├─ specs/
    └─ plans/
```

### 폴더 승격 규칙

> **같은 성격의 문서가 3개 모이면 그때 폴더를 만든다. 미리 만들지 않는다.**

빈 폴더와 지켜지지 않는 규칙은 체계의 신뢰를 깎는다. 현재 `docs/README.md`가
ADR을 선언해놓고 0개인 것이 정확히 그 사례다.

따라서 ADR 전용 폴더를 지금 만들지 않는다. 결정 기록은
`notes/YYYY-MM-DD-결정-<주제>.md`로 시작하고, 3개가 쌓이면 `decisions/`로
승격한다. 운영 런북도 `guides/operations.md` 한 장으로 시작해서 늘어나면
`guides/runbooks/`로 승격한다.

구조가 실제 사용량을 따라가게 하고, 사용량이 구조를 따라가려다 실패하는
상황을 만들지 않는다.

### 이슈 기록 템플릿

**기록 기준: 코드와 커밋만 봐서는 복원할 수 없는 맥락인가.**

"중요도"가 아니라 "복원 가능성"이 기준이다. 이 기준이 있으면 매번 고민할
필요가 없다.

| 기록한다 | 기록하지 않는다 |
|---|---|
| 진단에 시간이 걸린 것 | 단순 오타·문구 수정 |
| 원인이 의외였던 것 | 코드를 보면 자명한 변경 |
| 재발 가능성이 있는 것 | 일회성 설정 변경 |
| 인프라·배포·보안 판단 | 리팩터링 |

예상 빈도는 주 1~3건이다.

**파일 위치**: `docs/issues/YYYY-MM-DD-<한국어-슬러그>.md`

**프론트매터** (키는 영문, 값은 한국어):

```yaml
---
date: 2026-07-15
kind: 디버깅          # 디버깅 | 인프라
area: 프론트엔드       # 프론트엔드 | 백엔드 | 배포 | 운영
tags: [비동기, 상태관리, 요청경합]
commits: [4419ab5, 0cda678, 519f25b]
---
```

프론트매터 키만 영문인 이유: 사람이 읽는 문장이 아니라 색인 스크립트가
파싱하는 데이터이며, 이후 정적 사이트 생성기나 검색 도구를 붙일 때 영문 키가
호환된다. 값은 모두 한국어로 유지한다.

**본문 4섹션** (`kind`에 따라 제목만 달라진다):

| `kind: 디버깅` | `kind: 인프라` | 담는 내용 |
|---|---|---|
| `## 증상` | `## 배경` | 무엇이 보였는가 / 왜 이 일이 필요했는가 |
| `## 원인` | `## 근거` | 진짜 원인 / 이 선택을 한 이유와 버린 대안 |
| `## 해결` | `## 조치` | 무엇을 어떻게 고쳤나 + 파일 경로 |
| `## 교훈` | `## 주의사항` | 일반화되는 패턴 / 건드릴 때 조심할 것 |

**네 번째 섹션이 이 문서의 존재 이유다.** 앞의 세 섹션은 대부분
`git show <sha>`로 복원된다. 복원 불가능한 것은 "이게 일반화되는 패턴이고
새 화면을 만들 때 미리 막아야 한다"는 판단뿐이다.

> 교훈을 쓸 수 없다면 그 이슈는 기록할 가치가 없다.

**작성 예시**:

```markdown
---
date: 2026-07-15
kind: 디버깅
area: 프론트엔드
tags: [비동기, 상태관리, 요청경합]
commits: [4419ab5, 0cda678, 519f25b]
---

# 좌석표 학교·반 전환 시 옛 응답이 최신 상태를 덮어씀

## 증상
학교 셀렉터를 빠르게 두 번 전환하면 이전 학교의 학생 명단이 화면에 남는다.
느린 네트워크에서 재현율 100%.

## 원인
`fetch` 응답 도착 순서는 요청 순서와 무관한데 도착하는 대로 상태를 덮어썼다.
A(느림) → B(빠름) 순으로 요청하면 B가 먼저 그려지고 A가 나중에 덮어쓴다.

## 해결
요청마다 세대(generation) 번호를 부여하고, 응답 처리 시점에 최신 세대가
아니면 버린다. 로딩 플래그도 같은 가드 안에서 함께 내린다.
→ `frontend/app/admin/seating/page.tsx`

## 교훈
**셀렉터로 전환 가능한 모든 비동기 목록에 같은 함정이 있다.**
이 프로젝트에서만 같은 뿌리로 3번 터졌다.
새로 "전환 + 비동기 로딩" 조합을 만들 땐 무효화 가드부터 넣고 시작한다.
```

### 색인 자동 생성

`docs/issues/README.md`를 손으로 유지하면 반드시 낡는다 — 현재
`docs/README.md`가 낡은 것과 같은 이유다. 스크립트로 생성한다.

**`scripts/gen-docs-index.py`**

- Python 표준 라이브러리만 사용한다. 의존성 0.
- 프론트매터 필드가 5개이고 형식이 고정이라 정규식 파싱으로 충분하다.
  PyYAML을 추가할 이유가 없다.
- `docs/issues/*.md`를 읽어 `docs/issues/README.md`의 표를 날짜 역순으로 생성한다.
- 프론트매터가 없거나 필수 키가 빠진 파일은 경고를 출력하고 건너뛴다.
  실패로 중단하지 않는다 — 색인 생성이 작업을 막으면 아무도 쓰지 않게 된다.
- `README.md` 자신은 대상에서 제외한다.

생성 결과:

| 날짜 | 제목 | 영역 | 태그 |
|---|---|---|---|
| 2026-07-15 | [좌석표 요청 경합](2026-07-15-…) | 프론트엔드 | 비동기, 상태관리 |

CI 연동은 하지 않는다. 문서를 추가할 때 수동 실행하고, 실행을 잊어도 문서
자체는 온전하다.

| `CLAUDE.md`, `AGENTS.md` | **유지** — 코드 옆에 있어야 하는 에이전트 지침 |

이동은 모두 `git mv`로 수행해 `git log --follow`가 이력을 추적할 수 있게 한다.

### 백필 대상

과거 커밋에서 역으로 이슈 기록을 만든다. 선정 기준은 **여러 커밋에 흩어져
있어 종합이 필요한 것**이다. 단일 커밋으로 완결된 문제는 커밋 본문으로 충분하다.

| # | 주제 | 묶는 커밋 | `kind` | `date` |
|---|---|---|---|---|
| 1 | 전환 시 이전 대상의 상태가 남는 문제 | `4419ab5` `0cda678` `519f25b` `d59c209` `20665a3` | 디버깅 | 2026-08-01 |
| 2 | 새 fetch마다 401 처리를 반복해서 누락 | `978be6c` `3c4b277` `87995e5` | 디버깅 | 2026-08-02 |
| 3 | 환경변수 가드 부재로 잘못된 값이 조용히 기동됨 | `5bfddbf` `8e91330` | 인프라 | 2026-08-02 |

백필 문서의 `date`는 해당 커밋 중 **마지막 커밋 날짜**를 쓴다. 문제가 종결된
시점이 기록 시점이다.

**#1의 범위 주의**: 다섯 커밋이 같은 증상(전환 후 이전 대상의 데이터가 보임)을
내지만 메커니즘은 두 갈래다.

- `4419ab5`·`0cda678`·`519f25b` — 응답 도착 순서가 요청 순서와 달라서 생기는
  경합. 세대(generation) 번호로 해결.
- `d59c209`·`20665a3` — `student` prop이 바뀐 첫 렌더에서 초기화 `useEffect`가
  아직 돌지 않아 이전 상태가 그려짐. 렌더 시점 조건(`detail?.id !== student.id`)으로 해결.

문서에서 이 둘을 구분해 적고, 교훈은 "전환 가능한 UI에서는 *로딩 플래그만으로
판단하지 말고 데이터의 소속을 확인하라*"로 묶는다. 메커니즘을 뭉뚱그리면
다음에 재발했을 때 어느 쪽 처방을 쓸지 알 수 없다.

**백필에서 제외한 커밋**:

- `a38e94a`(생성 엔드포인트 무인증 → 학생 토큰 요구)는 401 *처리 누락*이 아니라
  인증을 애초에 걸지 않은 문제다. 커밋 본문에 이미 배포 순서 주의사항까지
  적혀 있어 추가 종합이 필요 없다.
- `d443159`(`compare_digest` 비-ASCII 500), `a5c41ea`(시크릿 기본값 차단)는
  각각 단일 커밋으로 완결됐고 본문 설명이 충분하다.

단일 커밋으로 끝났고 본문이 충분한 건은 백필하지 않는다. 문서의 값어치는
흩어진 것을 묶는 데서 나오므로, 커밋 하나를 그대로 옮겨 적는 것은 중복이다.

### 신규 문서

**`docs/README.md`** — 전면 재작성. 현재 내용은 모노레포 이전 기준이라
사실과 다르다. 새 README가 담을 것:

- 폴더별 성격과 수명 (살아있음/박제)
- 어떤 문서를 어디에 쓸지 판단하는 규칙
- 폴더 승격 규칙
- `guides/` 목록과 한 줄 설명
- `issues/`·`notes/` 색인 링크

**`docs/issues/README.md`** — 스크립트 생성. 초기엔 백필 3건.

**`docs/guides/operations.md`** — 행사 운영 런북. 신규 작성하되 이번엔
**뼈대와 이미 아는 내용만** 채운다. 헬스체크 URL, 배포 트리거, 장애 시 확인
순서 등 `DEPLOYMENT.md`와 `2026-08-08-행사-부하-용량-점검.md`에서 끌어올 수
있는 것에 한정한다. 추측으로 채우지 않는다.

**`CLAUDE.md` 문서 규칙 절** — 새 구조에 맞춰 재작성. 에이전트와 팀원이 같은
판단을 하도록 "어떤 문서를 어디에 쓰는가"를 명시한다.

## 검증

문서 변경이므로 자동 테스트 대상은 스크립트뿐이다.

1. `scripts/gen-docs-index.py`를 백필 3건에 대해 실행 → 표가 날짜 역순으로
   정확히 생성되는지 확인.
2. 프론트매터가 없는 파일을 넣고 실행 → 경고 후 계속 진행하는지 확인.
3. 모든 문서 내부 상대 링크가 이동 후에도 유효한지 확인 (수동 grep).
4. `git log --follow`로 이동한 파일의 이력이 보존됐는지 확인.
5. `README.md`(루트)와 `docs/README.md`의 모든 링크를 클릭 확인.

코드 변경이 없으므로 `backend`/`frontend` 품질 게이트는 해당 없다.
