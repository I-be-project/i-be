# 부스 존·역량과 QR 일괄 발급 — 설계

작성 2026-09-11. 부스 명단은 [`../../guides/booths.md`](../../guides/booths.md).

## 배경

행사장 부스 67개(직업체험 57 + 역량체험 10)를 시스템에 올려야 한다. 지금 있는 것은
부스 1건씩 등록하는 관리자 화면, 6자 코드 자동 발급, QR PNG 개별 다운로드,
학생 QR 방문 기록, 부스별 참여 통계다. 동작은 다 하지만 67개 규모를 감당하지 못한다.

- 등록: 관리자 화면에서 67번 입력해야 한다.
- 찾기: 목록이 평평해서 존을 구분할 수 없다.
- 인쇄: QR을 한 장씩 모달로 열어 67번 내려받아야 한다.
- 차트: 학생 성향 탭의 레이더 차트가 **부스를 축으로** 삼는다
  (`frontend/app/(tabs)/tendency/page.tsx`). 부스마다 방문 여부를 0/1로 찍는 구조라
  부스가 67개가 되면 축 67개로 무너진다.

## 목표

1. 부스 67개를 존과 함께 한 번에 등록한다.
2. QR을 존별로 한 번에 인쇄한다.
3. 참여 현황을 존별로 본다.
4. 성향 탭 차트의 축을 부스에서 **역량 10개**로 바꾼다.

## 역량 10개

국가직무능력표준(NCS) 직업기초능력 기반. 값은 고정이고 순서는 차트 축 순서다.

| 키 | 역량 | 역량체험존 부스명(안) |
|---|---|---|
| `communication` | 의사소통 | 스피치ON |
| `creativity` | 창의성 | 창의ON |
| `analysis` | 분석력 | 탐구ON |
| `challenge` | 도전정신 | 도전ON |
| `empathy` | 공감 | 마음ON |
| `collaboration` | 협업 | 함께ON |
| `thinking` | 사고력 | 해결ON |
| `judgment` | 판단력 | 선택ON |
| `self_understanding` | 자기이해 | 발견ON |
| `planning` | 계획성 | 성장ON |

DB와 API는 영문 키를 쓰고, 화면 라벨(한글)은 프론트 상수 한 곳에서 매긴다.

## 점수 계산

부스 한 곳을 방문하면 **그 부스에 연결된 역량이 각각 1점** 오른다.

- 직업체험 부스(F·L·Y존)는 역량 3개가 연결되므로 3개 축이 1점씩 오른다.
- 역량체험 부스(C존)는 자기 역량 1개가 연결되므로 1개 축이 1점 오른다.
- 가중치도 상한도 두지 않는다. 방문 기록은 부스당 1건이라 같은 부스로 점수를 부풀릴 수 없다.

점수는 저장하지 않는다. `booth_visits`와 연결 테이블을 조인해 조회 시점에 센다.
전체가 학생 1명당 최대 67행이라 집계 비용이 문제되지 않고, 매핑이 고쳐지면 점수가
따라 고쳐진다. 점수를 따로 저장하면 매핑을 고칠 때 재계산이 필요해진다.

## 데이터 모델

**마이그레이션 `0013_add_booths_zone.sql`** — `ops.booths`에 `zone` 컬럼.

| 값 | 존 |
|---|---|
| `F` | 직업체험 F(Future)존 |
| `L` | 직업체험 L(Love)존 |
| `Y` | 직업체험 Y(Yourself)존 |
| `C` | 역량체험존 |

`text not null default ''` + 체크 제약 `zone in ('F','L','Y','C','')`. 기존 행과 존을
모르는 부스는 빈 문자열로 남는다. 존 테이블은 만들지 않는다. 값이 4개로 고정이고
이름도 바뀌지 않는데 테이블을 만들면 조인만 는다.

**마이그레이션 `0014_create_booth_competencies.sql`** — 부스↔역량 연결.

```
ops.booth_competencies (
    booth_id   uuid not null references ops.booths (id) on delete cascade,
    competency text not null check (competency in (
        'communication','creativity','analysis','challenge','empathy',
        'collaboration','thinking','judgment','self_understanding','planning'
    )),
    primary key (booth_id, competency)
)
```

- 부스 하나에 역량 여럿, 역량 하나에 부스 여럿이라 연결 테이블이다. 컬럼 3개로 두면
  "이 역량을 다루는 부스" 조회가 3열 OR이 되고 개수가 바뀔 때 스키마가 또 바뀐다.
- "정확히 3개"는 DB 제약으로 걸지 않는다. 역량체험 부스는 1개고, 자료가 오기 전에는
  0개다. 개수 규칙은 시드 스크립트가 검사한다.
- 역량 테이블은 만들지 않는다. 10개가 고정이고 이름도 바뀌지 않는다. 체크 제약과
  코드 상수로 충분하다.
- 역방향 인덱스(`competency`)는 두지 않는다. 전체가 200행 미만이다.

## 이름 규칙

| 존 | `name` | `description` |
|---|---|---|
| F·L·Y | 체험주제 | 기관(업체)명 |
| C | 부스명(안) | 미션 활동 |

학생에게는 기관명보다 무엇을 하는지가 먼저 보여야 한다. 같은 기관이 부스를 여럿
운영하므로(국제메타미디어콘텐츠협동조합 3개, 충남대 생활과학교실 2개) 기관명을 이름으로
쓰면 목록에서 구분되지 않는다.

체험주제 57개는 서로 모두 다르고 가장 긴 것이 34자라 `name`의 100자 제한 안에 든다.
이름이 고유하다는 성질은 시드 스크립트의 중복 판별에도 쓴다.

## 등록 — CSV + 시드 스크립트

`backend/scripts/seed_booths.py`. 기존 `export_students.py`와 같은 방식으로 **관리자 API만
호출한다.** DB에 직접 붙지 않는다.

```
uv run python -m scripts.seed_booths \
    --base-url https://api.cnu-likelion.kr \
    --username admin --password '<비밀번호>' \
    --csv scripts/booths.csv [--dry-run]
```

- 입력 CSV(`backend/scripts/booths.csv`)는 `zone,name,description,competencies` 4열.
  `competencies`는 역량 키를 `;`로 이어 쓰고, **지금은 전부 빈 칸으로 둔다.**
- 실행하면 먼저 `GET /api/admin/booths`로 기존 목록을 받아 **이름이 같은 부스는 건너뛴다.**
  중간에 실패해도 다시 돌리면 안 들어간 것만 들어간다.
- 이미 등록된 부스의 역량은 갱신한다. 주최측 자료가 오면 CSV의 역량 칸만 채워 다시
  돌리는 것으로 끝난다. 이름·설명·존은 갱신하지 않는다(관리자 화면에서 고친다).
- 역량 칸이 비어 있지 않으면 개수와 키를 검사한다. F·L·Y존은 3개, C존은 1개가 아니면
  등록을 멈추고 몇 행이 틀렸는지 알린다.
- `--dry-run`은 무엇이 새로 등록·갱신되는지만 출력한다.

DB에 직접 붙지 않는 이유는 코드 발급이다. 6자 코드는 혼동 문자를 뺀 랜덤 값이고 충돌 시
재시도까지 서비스가 처리한다. SQL로 값을 박으면 그 로직을 우회하게 된다.

## QR 일괄 인쇄

`/admin/booths/print` 페이지를 추가한다.

- 존 선택(F·L·Y·C·전체) → 해당 부스의 QR을 격자로 깔고 브라우저 인쇄(`window.print()`)를 쓴다.
- QR 이미지는 이미 있는 `frontend/lib/boothQr.ts`의 `renderBoothQrPng`를 그대로 쓴다.
  새 의존성도 PDF 생성기도 넣지 않는다.
- 한 장에 QR, 체험주제, 기관명, 6자 코드를 함께 찍는다. 카메라가 안 잡힐 때 학생이 코드를
  손으로 입력할 수 있어야 한다.
- 인쇄용 CSS는 `@media print`로 배경·네비게이션을 숨기고 칸이 쪽 경계에서 잘리지 않게 한다.

QR 링크의 base는 서버가 `FRONTEND_ORIGIN`으로 조립해 내려주므로, 로컬 개발 서버에서
인쇄해도 인쇄물에 `localhost`가 박히지 않는다.

## 화면

**성향 탭 (학생).** 차트 데이터를 부스에서 역량으로 바꾼다. 축은 항상 10개로 고정이라
부스가 몇 개로 늘어도 차트가 무너지지 않는다. `recharts`는 이미 쓰고 있어 의존성 변화가 없다.

매핑이 아직 비어 있는 동안에는 방문을 해도 모든 축이 0이 된다. 이때는 차트 대신 기존
빈 상태 안내를 띄운다. 0점짜리 차트는 고장으로 보인다.

**부스 탭 (학생).** 그대로 둔다. 방문한 부스 이름을 나열하는 화면이라 역량과 무관하다.

**관리자.** 부스 목록에 존 컬럼과 존 필터, 등록·수정 폼에 존 선택을 넣는다. 참여 통계는
기존 응답을 그대로 받아 **프론트에서 존으로 묶어** 보여준다. 통계 API는 바꾸지 않는다.
67행을 화면에서 묶는 데 서버 집계가 필요하지 않다.

## API 변경

| 대상 | 변경 |
|---|---|
| `BoothCreateRequest` | `zone`·`competencies` 추가 (둘 다 선택) |
| `BoothUpdateRequest` | `zone`·`competencies` 추가 (부분 수정) |
| `BoothResponse` | `zone`·`competencies` 추가 |
| `ProfileSummary` | `competencies` 추가 — 10개 역량의 키·라벨·점수 |
| `StudentBoothResponse` | 바꾸지 않는다 |

`ProfileSummary.competencies`는 **점수가 0인 역량도 10개 모두** 내려준다. 프론트가 축을
채우려고 빠진 역량을 메울 필요가 없다.

외부 공개 문서(`docs/guides/admin-api.md`)는 부스 API를 다루지 않으므로 영향이 없다.
`docs/guides/architecture.md`의 부스 항목은 함께 갱신한다.

`code`는 그대로 불변이다. 인쇄물에 박히기 때문이다.

## 결정과 근거

**점수를 저장하지 않고 조회 때 센다.** 매핑이 나중에 오고, 온 뒤에도 고쳐질 수 있다.
점수를 저장하면 매핑을 고칠 때마다 전교생 점수를 재계산해야 한다. 조인 한 번이 더 싸다.

**매핑이 비어 있어도 지금 만든다.** 주최측 자료를 기다리되 스키마·API·차트는 먼저 세운다.
자료가 오면 CSV의 역량 칸을 채워 시드를 다시 돌리는 것으로 끝난다.

**존은 컬럼, 역량은 연결 테이블.** 부스는 존 하나에만 속하고 역량은 여럿과 이어진다.
구조가 다르므로 저장 방식도 다르다.

**시드를 SQL 마이그레이션에 넣지 않는다.** 코드 발급 로직을 우회하면 인쇄물과 DB가
어긋날 여지가 생긴다.

## 미해결

- **부스별 역량 3개 매핑은 주최측 자료를 기다린다.** 도착 전까지 차트는 빈 상태로 보인다.
  자료가 없이 행사가 가까워지면 체험주제를 보고 배정하는 방법을 다시 논의한다.
- 역량체험 부스 10개의 이름은 주최측 자료에 "부스명(안)"으로 되어 있다. 확정되면 `name`만
  고친다. `code`는 그대로 둔다.
- 부스 명단 자체가 행사 전까지 바뀔 수 있다. 바뀌면 CSV를 고치고 시드를 다시 돌린다.
